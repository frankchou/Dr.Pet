## 產品概覽

**PurePaw 無敏毛孩** 是專為台灣飼主打造的 AI 寵物營養健康管理平台，核心功能為即時掃描寵物食品成分、AI 個人化飲食建議、健康日誌追蹤。前身品牌為「寵物隨行醫師 Dr. Pet」，v2.0.0 起全面更名。

## 版面架構（RWD）

```
root layout (src/app/layout.tsx)
├── ClientShell          ← 身份驗證 + 免責聲明守衛
│   ├── Sidebar          ← 桌面左側欄（md 以上顯示，w-64 fixed）
│   └── main content area
│       ├── {page children}
│       └── BottomNav    ← 手機底部導覽列（md 以下顯示）

/landing（獨立 layout，不套用 App shell）
└── landing/layout.tsx   ← 覆蓋父層 layout，僅回傳 children，無 Sidebar/BottomNav/ClientShell
```

Landing page 使用 `src/app/landing/layout.tsx` 覆蓋父層 layout，完全跳過 `ClientShell`、`Sidebar`、`BottomNav`，適合對外公開的行銷頁面。

**手機（< md）**：底部導覽列 `BottomNav`，高度 60px，含 4 個分頁 tab + 中央凸起相機 FAB。導覽固定 5 項，順序為 **毛孩(`/`)｜飲食(`/diet`)｜照相(`/scan`，中央 FAB)｜日誌(`/diary`)｜快訊(`/news`)**。Active tab 以 `bg-[#111111] text-white rounded-2xl` 圓角黑底 icon 指示器呈現。頂部 sticky header 左上角顯示使用者頭像（手機限定，`AppShell` 內），點擊開啟 ProfileMenu（切換毛孩 / 設定 / 登出），對齊桌面 Sidebar 的使用者選單；右上角鈴鐺按鈕導向 `/news`。
**桌面（>= md）**：左側欄 `Sidebar`，寬 256px fixed；主內容區 `ml-64` 偏移。桌面 header 左側改顯示頁面標題與副標題。導覽與手機一致，順序為 **毛孩｜飲食｜照相｜日誌｜快訊**。

**導覽隱藏項**：「營養分析(`/nutrition`)」與「AI 諮詢(`/nutritionist`)」兩個入口已自 Sidebar 與 BottomNav 移除（`NAV_ITEMS` / `RIGHT_NAV_ITEMS` 內加註說明），**頁面與路由皆保留**，日後把項目加回 nav 即可恢復。

**Viewport 設定**：`src/app/layout.tsx` 匯出 `export const viewport = { viewportFit: 'cover' }`，讓 `env(safe-area-inset-*)` 在手機上大於 0，配合 bottom-sheet modal 底部安全區 padding 真正生效（home indicator 不擋住按鈕）。

**AI 諮詢頁（`/nutritionist`）例外 layout**：`AppShell` 偵測 `isChat = pathname === '/nutritionist'`，對 `<main>` 切換 `overflow-hidden`（停用頁面 scroll），不渲染 sticky header，content wrapper 改為 `h-full`。頁面內部分三 flex 區：頂部 `shrink-0`（標題 + 免責聲明 + 寵物切換）、中間 `flex-1 min-h-0 overflow-y-auto`（唯一 scroll 區）、底部 `shrink-0`（輸入列）。

## API Endpoints

> **AI/外部端點依帳號分流總則**：所有會呼叫 Anthropic 或外部搜尋的端點，一律「先 `auth()` + 既有權限檢查 → 再判 `isDemoUser(session)`」；**demo 帳號（`demo-user` / `demo@drpet.com`）→ 回固定 mock（不打 AI、不打外部搜尋）；測試帳號與真實環境帳號 → 走真實 AI / 外部搜尋**。mock 結構嚴格符合各端點既有回傳型別，前端不需改。涵蓋 15 支（analyze、chat、diary-parse、diet-analysis、extract、instant-analyze、month-summary、nutrition-ai、products/lookup、products/web-search、recommend、switch-plan-ai、symptoms/advice、tasks、news GET）；`news/crawl`（排程生成、非帳號觸發）**不分流**，維持真 AI。詳見系統機制「demo 帳號全 mock 分流機制」。

| 路徑 | 方法 | 功能 |
|------|------|------|
| `/api/extract` | POST | 視覺 AI 擷取食品標籤成分 |
| `/api/instant-analyze` | POST | 照片 → 成分安全判讀（safe/caution/danger），存 `InstantAnalysis` |
| `/api/chat` | POST | AI 對話，注入寵物背景資料為 system prompt |
| `/api/analyze` | GET / POST | GET：依 `?petId=` 取該寵物最新一筆 `AIInsight`（關聯分析顯示端）；POST：跑相關性分析並存 `AIInsight` |
| `/api/nutrition-ai` | POST | AI 營養摘要（產品堆疊） |
| `/api/recommend` | POST | AI 產品推薦 |
| `/api/tasks` | POST | 生成每週照護任務清單 |
| `/api/analysis` | GET | 規則式成分知識庫分析（不呼叫 AI）。**Phase 6 補上 demo 分流**：通過 `requirePetAccess` 後，`isDemoUser(session)` → 回固定 `DEMO_ANALYSIS`（`src/lib/demoAnalysis.ts`，結構與正常路徑回傳 body 完全一致） |
| `/api/product-report` | POST | **Phase 6 新增**。產品資料錯誤回報：需登入；帶 `productId`（+選填 `note`）；**所有帳號（含 demo）皆寫入 `ProductErrorReport`**，寫入成功即回 `{ ok: true }`；接著寄信通知 `purepaw.notify@gmail.com`（沿用 `src/lib/email.ts` Gmail SMTP），寄信失敗 try/catch 記 log、不影響 API 成功。信件主旨依環境前綴 `[測試]`（`DATABASE_URL` 以 `file:` 開頭）/`[正式]`（Turso），內文帶產品名/品牌/productId/回報者 userId/是否 demo/note |
| `/api/feedback` | POST | **Phase 6-9 新增**。使用者選單「問題回報」：需登入；body `{ content, category? }`；`content` 必填、trim 後非空、上限 2000 字（超過回 400）；`category` 選填且須為 4 項白名單之一（`src/lib/feedback.ts` `FEEDBACK_CATEGORIES`），非白名單值落為 `null`；輕量防連發（同 userId + 完全相同 content 於 60 秒內已寫入 → 視為重複，不重複寫直接回 `{ ok: true }`）；**所有帳號（含 demo）皆寫入 `Feedback`** 後寄信 `purepaw.notify@gmail.com`，寄信 try/catch 失敗不擋 API。userId 一律取自 `auth()` session |
| `/api/reviews` | POST / GET | **Phase 6-9 新增**。POST 使用者選單「評論／評分」：需登入；body `{ rating, comment? }`；`rating` 須為 1-5 整數、`comment` 選填上限 1000 字；**評論頻率限制**——寫入前查該 userId 最近 30 天是否已有 `AppReview`，有則回 **429**（訊息含下次可評論日期），是月限制的最終防線；**所有帳號（含 demo）皆寫入 `AppReview`** 後寄信，寄信失敗不擋 API。GET 公開評論列表：僅回 `isPublic=true && status='approved'` 的評論（`select` 只取 id/rating/comment/createdAt，不回 userId/email）+ `averageRating` + `count`；`export const dynamic = 'force-dynamic'` 不快取，供 `AppReviewsList` 用（目前由旗標隱藏）。型別 `PublicReviewsResponse` 由 route 匯出供前端共用 |
| `/api/reviews/eligibility` | GET | **Phase 6-9 新增**。評論資格預檢：需登入；查該 userId 最近 30 天是否已有 `AppReview`，回 `{ canReview, nextAvailable? }`（不可評論時 `nextAvailable` 為 ISO 字串）。供 `ReviewModal` 開啟當下查詢、提早告知已評論者，避免白填；`force-dynamic` 不快取。型別 `ReviewEligibilityResponse` 匯出供前端共用 |
| `/api/meal-plans/[id]/items` | POST / PATCH / DELETE | 配餐品項 CRUD。**Phase 6 新增 PATCH**：接 `itemId` + `quantity`，以 `requirePetAccessByRecord('dailyMealPlan', planId, userId)` 依該 plan 的 pet 驗權，再 `findFirst({ id: itemId, planId })` 確認 item 屬該 plan（防越權），驗證 `quantity` 為 `> 0 且 <= 9999` 有限數字後更新 `MealPlanItem.quantity`，回傳更新後 item（含 product） |
| `/api/news/crawl` | GET / POST | AI 生成寵物食安/危險禁忌/健康知識三類快訊並寫入 `NewsArticle`。GET 供 Vercel Cron 每日觸發、POST 供手動觸發，兩者皆以 `Authorization: Bearer <CRON_SECRET>` 授權；prompt 附 `VET_REFERENCE_SCOPE`，近 7 天「同分類同標題」去重。**全站公開、非 pet-scoped** |
| `/api/symptoms/advice` | GET | 依該毛孩、該症狀類型近 30 筆紀錄生成 AI「可能原因／建議做法」（pet-scoped，`requirePetAccess` 先擋再呼叫 AI）。結果快取於 `AIInsight`；`?refresh=1` 強制重生。無紀錄回 `{ advice: null }` 不打 AI |
| `/api/month-summary` | GET | 依 `?petId=&yearMonth=YYYY-MM` 後端聚合當月 `DailyHealthLog`，再請 AI 生白話健康解讀摘要（pet-scoped，`requirePetAccess` 先擋）。程序內 Map 快取（上限 200、近 LRU 淘汰、依 statsHash 命中）；無資料回 `{ summary: null }` |

## Web Push 推播架構（Phase 5）

PurePaw 以標準 **Web Push（VAPID）** 對使用者裝置送系統通知，分兩類：**食安警報**與**用藥/美容提醒**。各部分職責如下：

| 部分 | 位置 | 職責 |
|------|------|------|
| 訂閱資料 model | `prisma/schema.prisma` `PushSubscription` | 一裝置一筆（`endpoint @unique`），存 `userId`（關聯 `User`、`onDelete Cascade`）、加密金鑰 `p256dh` / `auth`、兩個偏好開關 `foodAlertEnabled` / `reminderEnabled`（皆預設 true）、`createdAt`；`@@index([userId])`。`User` 補 `pushSubscriptions PushSubscription[]` relation |
| Service Worker | `public/sw.js`（純 JS，不經 Next 編譯，根路徑 `/sw.js`） | 處理 `install`/`activate`（skipWaiting + clients.claim 讓新版即時接管）、`push`（解析 payload 顯示系統通知；個人化頭條 `headline`/`priority:'high'` 時改用 `requireInteraction`/`renotify`/`vibrate` 顯示更顯眼）、`notificationclick`（聚焦既有同源視窗並導向 `data.url`，否則開新視窗，預設 `/news`）|
| 送推 helper | `src/lib/push.ts`（VAPID 私鑰唯一使用點） | `sendPush()` 送單筆、失效訂閱（410/404）自動刪 DB；`sendPushToUser()` 依 kind 過濾開關後送該使用者全部訂閱，**demo userId 一律改送固定 mock**；`sendInBatches()` 每批 50 筆 `Promise.allSettled` 分批並行。VAPID 採延後設定（首次送推才讀 env，避免 build 期報錯）|
| 食安觸發 | `src/app/api/news/crawl/route.ts` `triggerFoodAlertPush()` | 快訊 cron 生成後接著觸發；取「urgent food_safety 且未推」的快訊送給開啟食安推播的訂閱者，並依飼主使用中產品做個人化頭條比對 |
| 提醒 cron | `src/app/api/reminders/check/route.ts` | 每日掃到期的用藥/美容提醒並送推 |

## 資料庫架構重點

- `Pet` 為核心實體，幾乎所有模型均以 Pet delete 為級聯刪除對象。
- 陣列型欄位（如 `mainProblems`、`allergies`、`photos`）儲存為 JSON 字串，讀取須用 `parseJson()`（位於 `src/lib/utils.ts`）。
- `PetProduct` 管理寵物的固定／試用產品清單（`listType: "fixed" | "trial"`）。
- `ProductReaction` 記錄每日產品反應評分，唯一約束 `@@unique([petId, productId, date])`。
- `HealthMetric` 記錄每日健康指標（BCS 體態評分 1–9、活力 low/medium/high、水分 low/medium/high），唯一約束 `@@unique([petId, date])`。
- `DailyHealthLog` 記錄每日完整健康狀態日誌（食慾/飲水/排便/泌尿/活力/情緒/皮毛/眼耳/牙齒/消化/呼吸/神經/生殖），唯一約束 `@@unique([petId, date])`；多選欄位以 JSON array string 儲存。
- `MedicationRecord` 記錄用藥與看診事件（疫苗/驅蟲/處方/看診備注均為 JSON array），支援照片與下次提醒日期；**Phase 5 新增 `reminderIntervalDays Int?`**（null=一次性、>0=每 N 天循環）。
- `GroomingRecord` 記錄洗澡美容事件，分自洗/外送兩種模式，四個進階療程各有獨立欄位，支援照片與下次提醒日期；**Phase 5 新增 `reminderIntervalDays Int?`**（同上）。
- `PushSubscription`（**Phase 5 新增**）記錄使用者裝置的 Web Push 訂閱：一裝置一筆（`endpoint @unique`），關聯 `User`（`onDelete Cascade`），存加密金鑰 `p256dh` / `auth` 與兩個偏好開關 `foodAlertEnabled` / `reminderEnabled`，`@@index([userId])`。
- `MeasurementRecord` 記錄量測追蹤數值（體重/BCS/RRR/血糖/血壓/體溫）。
- `NewsArticle` 記錄健康快訊（分類 food_safety / danger / health、是否緊急、來源連結），由 `/api/news/crawl` 的 AI 生成寫入；**Phase 5 新增 `affectedBrands String?`**（食安警報涉及的廠商/品牌/產品關鍵詞 JSON array，供個人化頭條比對）與 `foodAlertPushedAt DateTime?`（已觸發食安推播的時間戳，非 null=已推、防重複）。
- `AIInsight` 除原本的關聯分析用途外，**Phase 4 起亦兼作「症狀詳情頁 AI 建議」的快取表**：每筆建議存成一列，`symptomType` 為該症狀類型、`rationale` 存「可能原因」、`recommendedActions` 存建議陣列，並把「依紀錄算出的 sha1 dataHash」塞進本功能未使用的 `suspectedTriggers` 欄位（格式 `["__hash__:<hash>"]`）作為快取鍵；沒新紀錄時 hash 不變即回快取，不重打 AI。
- `DailyMealPlan` 為單日配餐計畫（`@@unique([petId, date])`），底下掛多筆 `MealPlanItem`（早/午/晚餐項目，可關聯 `Product` 或自填品名、份量、估重、標籤）。
- `ProductErrorReport`（**Phase 6 新增**）記錄使用者對某產品資料的錯誤回報：`productId`（關聯 `Product`、`onDelete Cascade`）、`userId`、`note String?`、`status @default("pending")`、`createdAt`。migration `20260610110000_add_product_error_report` 已套用於 dev.db（用 `db execute` 建表 + `migrate resolve --applied` 非破壞性對齊，未 reset）；正式庫（Turso）留 deploy 時跑 `prisma migrate deploy`。
- `Feedback`（**Phase 6-9 新增**）記錄使用者選單「問題回報」送出的文字問題：`userId`、`content String`、`category String?`、`status @default("pending")`、`createdAt`。**不綁 Pet、無外鍵**（沿用 `ProductErrorReport` 的輕量單一使用者模型）。
- `AppReview`（**Phase 6-9 新增**）記錄使用者選單「評論／評分」送出的 App 評論：`userId`、`rating Int`（1-5）、`comment String?`、`isPublic Boolean @default(false)`（控制是否進入公開評論列表）、`status @default("pending")`（供日後審核）、`createdAt`。同樣不綁 Pet、無外鍵。
- 上述兩表 migration `20260610120000_add_feedback_app_review` 已用相同非破壞性方式套用於 dev.db；正式庫（Turso）留 deploy 時跑 `prisma migrate deploy`。
- `NewsArticle`、`DailyMealPlan`、`MealPlanItem` 三個 model 早已存在於 migration、實際 DB 與程式碼中，但 `schema.prisma` 一度缺漏；現已補回，使 schema 與資料庫一致。
- Prisma v7 的 `DATABASE_URL` 不放在 `schema.prisma`，改由 `prisma.config.ts` 設定，runtime 於 `src/lib/prisma.ts` 建立帶 libsql adapter 的 `PrismaClient`。

### Vercel Cron 排程設定（`vercel.json`）

目前有兩個每日排程，設定於 `vercel.json`：

```json
{ "crons": [
  { "path": "/api/news/crawl",      "schedule": "0 2 * * *" },
  { "path": "/api/reminders/check", "schedule": "0 0 * * *" }
] }
```

- **快訊 AI 生成**：每日 02:00 UTC（台灣 10:00）以 **GET** 觸發 `/api/news/crawl`；生成完成後接著觸發食安警報推播（見系統機制）。
- **用藥/美容提醒**：每日 00:00 UTC（台灣 08:00，早上提醒當日待辦）以 **GET** 觸發 `/api/reminders/check`。

正式站由 Vercel 自動帶 `Authorization: Bearer $CRON_SECRET`。`CRON_SECRET` 需於 Vercel → Settings → Environment Variables 設定，否則授權一律失敗。

### `.env` 與 `.env.local` 的分工（本機開發 vs 正式環境）

| 檔案 | 用途 | 誰會讀 |
|------|------|--------|
| `.env` | 保留**正式環境**的設定（`DATABASE_URL` 指向正式 Turso 資料庫） | Vercel 正式機、未明確覆蓋時的本機 |
| `.env.local` | **本機開發覆蓋檔**，把 `DATABASE_URL` 指回本機 `dev.db` | 僅本機（Next.js 載入順序中 `.env.local` 優先於 `.env`；**Vercel 不讀此檔**） |

**兩個實體資料庫完全切開（frank 對齊的資料策略）**：

- **測試環境（Codespace）連 `dev.db`**：靠 `.env.local` 覆蓋達成；正式機讀不到 `.env.local`，仍用 `.env` 的 Turso。兩個實體 DB 互不相干。
- **正式環境（Vercel）連 Turso**：與 `dev.db` 毫無關聯。
- **測試環境內**：demo 帳號=全 mock（AI/外部功能與推播內容在送出/回應當下換 mock，**從不寫進 DB**）；其他測試帳號=自己建立的真實測試資料（真的寫進 `dev.db`）。
- **正式站關閉 demo 登入口**：Vercel **不設** `DEMO_ENABLED` / `NEXT_PUBLIC_DEMO_ENABLED`，因此正式站沒有 demo 入口，**demo 完全不會碰到正式 Turso**。

詳細的「demo 走真實流程、只換內容 mock」設計見系統機制。
