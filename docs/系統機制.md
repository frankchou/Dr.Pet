## 使用者身份識別流程

`ClientShell`（`src/components/layout/ClientShell.tsx`）在客戶端 `useEffect` 中執行初始化判斷，流程如下：

```
頁面載入
  └─ ClientShell 掛載（ready = false，不渲染任何內容，避免 SSR hydration 不一致）
       └─ useEffect 執行
            ├─ 讀取 localStorage['purepaw_user_ack']
            │    ├─ 存在 → setIsLoggedIn(true)，接著檢查免責聲明
            │    └─ 不存在 → 顯示 LoginPage
            └─ setReady(true)
```

`ready = false` 期間回傳 `null`，確保 SSR 與 CSR 內容一致，避免 React hydration 警告。

## 免責聲明彈窗機制

**觸發條件**：NextAuth session 狀態為 `authenticated`，且當前用戶尚未同意免責聲明（`purepaw_disclaimer_ack_v1_${userId}` 在 localStorage 中不存在）。

**by-user 隔離設計**：免責聲明的儲存 key 包含 userId（`purepaw_disclaimer_ack_v1_${userId}`），不同帳號各自獨立。換帳號登入時，若新帳號尚未同意，會重新觸發免責聲明彈窗，確保每位使用者都確實閱讀並同意。

**彈窗行為**：

| 步驟 | 說明 |
|------|------|
| 顯示 | 覆蓋全畫面，`z-[60]`，手機版從底部滑入，桌面版居中彈窗 |
| 滾動偵測 | `onScroll` 事件監聽，距底部 < 16px 時啟用同意按鈕 |
| 短內容例外 | `useEffect` 初始化時若 `scrollHeight - clientHeight < 16`，直接啟用按鈕 |
| 同意 | 點擊按鈕後寫入 `purepaw_disclaimer_ack_v1_${userId} = '1'`，關閉彈窗 |
| 後續造訪 | 對應 userId 的 key 存在則不再顯示 |
| 公開頁例外 | `/landing`、`/invite` 等公開路徑完全跳過免責聲明邏輯 |

**條款內容**（7 條）：服務性質、非醫療診斷（加粗警語）、資訊正確性、個人化限制、緊急狀況、資料與隱私、同意條款。

**獸醫參考來源聲明**固定顯示於條款末尾，列出 WSAVA、AAFCO、FEDIAF、NRC、農業部等機構。

## 手機 / 桌面 ProfileMenu 與切換毛孩同步機制

桌面有 Sidebar 底部的使用者選單，手機則沒有左側欄，因此在 `AppShell` 的 sticky header 左上角放一顆頭像按鈕（手機限定，`md:hidden`），點擊開啟 **ProfileMenu**，內容與桌面對齊：切換毛孩 / 設定 / 登出。

**頭像顯示**：優先用 NextAuth `session.user.image`（Google 大頭貼），沒有則顯示名稱首字。名稱取 `session.user.name`，缺則回退 `localStorage['drpet_nickname']`。

**選單內容**：

| 區塊 | 行為 |
|------|------|
| 切換毛孩 | 列出 `GET /api/pets` 取得的所有毛孩，目前選取者標「(目前)」並以黑底頭像標示；點擊即切換 |
| 設定 | `router.push('/settings')` |
| 登出 | `signOut({ callbackUrl: '/' })` |

**切換毛孩的跨元件同步**：點擊某隻毛孩時 `switchPet()` 會：

```
switchPet(petId)
  ├─ localStorage.setItem('drpet_currentPetId', petId)
  ├─ window.dispatchEvent(new StorageEvent('storage', { key: 'drpet_currentPetId', newValue: petId }))
  ├─ setCurrentPetId(petId)   ← 更新本元件顯示
  └─ setShowMenu(false)
```

手動 dispatch `storage` event 是因為瀏覽器原生只在「其他分頁」改動 localStorage 時才觸發 storage event，同分頁內的改動不會自動通知。透過手動廣播，所有監聽 `drpet_currentPetId` 的元件（如 AppShell 本身、`/symptoms` 頁）能在同一分頁內即時同步當前毛孩。

**選單關閉**：監聽 `mousedown`，點擊選單外區域即關閉。

**鈴鐺按鈕**：header 右上角鈴鐺導向 `/news`（快訊）。

## 營養分析頁關聯分析顯示機制（`/nutrition`）

`/nutrition` 的「關聯分析」區塊由 `CorrelationInsights` 元件呈現，把 `/api/analyze`（POST 跑分析時）寫入的 `AIInsight` 拿出來顯示，讓既有資料有顯示端。

```
CorrelationInsights 掛載（依 petId）
  └─ GET /api/analyze?petId=
       └─ 後端 prisma.aIInsight.findFirst（where petId, orderBy createdAt desc）取最新一筆
            ├─ 有資料 → 顯示：可疑觸發因素、有益因素、建議行動、信心度、整體說明、更新日期
            └─ 無資料 → 顯示「尚無關聯分析」引導文案
```

**資料相容處理**：`suspectedTriggers` 在不同來源格式不一致——seed 寫的是字串陣列，AI 實際產出是物件陣列（`{ name, confidence, basis, action }`）。`triggerName()` 同時相容兩種，物件取 `name` 欄位、字串直接用，避免顯示出 `[object Object]`。各 JSON 欄位皆以 `parseJson()` 安全解析。

## AI 提示詞規範

所有 AI 呼叫均在 prompt 末尾附加 `VET_REFERENCE_SCOPE`（定義於 `src/lib/utils.ts`），內容為獸醫學術來源聲明，確保 AI 回應具備專業參考根據並主動提示使用者諮詢獸醫。

**pet-scoped AI route 的權限順序**：凡是綁定某隻毛孩的 AI route（症狀建議、月摘要、換食計畫、飲食搜尋等），一律「先 `auth()` 取 session → `requirePetAccess` 驗權 → **通過才呼叫 Anthropic**」，避免未授權者也能耗用 AI token。錯誤分流沿用全站慣例：餘額不足 402、API key 缺 401、其餘 500。

## demo 帳號全 mock 分流機制（Phase 4）

frank 拍板的核心原則：**demo 示範帳號的所有 AI / 外部功能一律回固定 mock**（不呼叫 Anthropic、不打外部搜尋），讓示範省成本、回應穩定可重現；**測試帳號與真實環境帳號則全走真實 AI / 外部搜尋**。

### 判定（`src/lib/demo.ts`）

`isDemoUser(session)`：`session.user.id === 'demo-user'`（`DEMO_USER_ID`）或 `session.user.email === 'demo@drpet.com'`（`DEMO_EMAIL`）任一命中即為 demo；session 為 null / 無 user 一律 false。判定值需與 `src/lib/auth.ts` 的 demo Credentials 設定一致。

### 套用順序（每支端點一致）

```
endpoint 進入
  ├─ auth() 取 session + 既有權限檢查（requirePetAccess / web-search 既有 IDOR 防護等，不變）
  └─ 通過後判 isDemoUser(session)
       ├─ demo → 直接 return 該端點既有回傳型別的固定 mock（完全不呼叫 Anthropic / 不打外部搜尋）
       └─ 非 demo → 走原本 AI / 外部路徑（含原本的 JSON 驗證、降級 fallback），行為完全不變
```

- mock 一律就近放各 route 的模組常數，結構嚴格符合各端點既有回傳型別，**前端不需任何改動**。
- 各 mock 內容彼此呼應同一隻示意毛孩情境（鮭魚低敏飲食、皮膚搔癢、磷/鈉偏高），具代表性。

### 覆蓋的 15 支端點

| 端點 | 方法 | demo mock 來源 |
|------|------|---------------|
| `api/analyze` | POST | `DEMO_ANALYSIS`（雞肉蛋白×皮膚搔癢關聯）建立 `AIInsight` |
| `api/chat` | POST | `DEMO_CHAT_REPLY`（固定問診式回覆 + 非診斷免責） |
| `api/diary-parse` | POST | `DEMO_DIARY_PARSE`（症狀 / 健康指標 / 飲食三類 records + summary） |
| `api/diet-analysis` | POST | `DEMO_DIET_ANALYSIS`（複製自前端 `MOCK_DIET_ANALYSIS`） |
| `api/extract` | POST | 依 `docType` 回 `DEMO_PRODUCT_EXTRACT` 或 `DEMO_MEDICAL_EXTRACT` |
| `api/instant-analyze` | POST | `DEMO_INSTANT_RESULT`（caution 範例，含成分 / concerns / positives） |
| `api/month-summary` | GET | `DEMO_MONTH_SUMMARY`（代表性月摘要句） |
| `api/nutrition-ai` | POST | `DEMO_NUTRITION_ANALYSIS`（safe / caution / warning 三狀態） |
| `api/products/lookup` | POST | `DEMO_LOOKUP_AI` 當 aiData，**仍走本地知識庫** `analyzeIngredients` 算 impact |

| `api/news` | GET | `DEMO_NEWS`（三分類各 2 筆），依 `category` query 過濾、**不讀 DB** |

### `news/crawl` 例外（不分流）

`/api/news/crawl`（快訊 AI 排程生成）**完全不碰**——它是全站排程、非帳號觸發（由 Vercel Cron 以 `CRON_SECRET` 觸發），維持真實 AI 生成。

### 落地 DB 與不落地的差別

- **會落地 DB 的 demo 路徑**（`analyze` / `nutrition-ai` / `recommend` / `tasks` / `instant-analyze`）**仍寫入 DB**，並沿用原本的寫入與清理邏輯（如 `NutritionAnalysis` 保留最近 3 筆、`recommend` 保留最新 1 筆、`tasks` 刪未完成舊任務再 createMany、`chat` 寫 user+assistant 兩筆 `ChatMessage`、`instant-analyze` 仍存上傳圖片並寫 `InstantAnalysis`），讓 GET / 歷史 / 重讀行為與真實帳號一致。
- **不落地的**（`diary-parse` 解析階段、`extract`、`products/lookup`、`web-search`、`news` 讀取）直接回 mock，不寫 DB。

### 原本無 auth 的端點處理（`extract` / `products/lookup` / `news` GET）

這三支原本不需登入。本次新增的 `auth()` **純為判 demo**，不對非 demo 加授權門檻：

- **只有「有 session 且為 demo 帳號」才回 mock**；無 session（一般訪客 / 未登入）或非 demo 帳號一律照原樣走真實流程（讀真實 DB / 走真實 vision / 走真實查詢），行為完全不變、不退化。

### 與既有「資料歸屬分流」的關係

本機制是**新增的「AI/外部功能」分流**；與既有的「一般資料歸屬分流」是兩件事、互補：

- **一般資料**（毛孩、日誌、配餐等）靠**同一資料庫內的 `userId` 歸屬**區隔——demo 帳號吃 seed 灌入的示範資料、真實帳號吃自己建立的資料。這是早已存在的設計，非本次新增。
- **AI/外部功能**則由本次的 `isDemoUser` 分流——demo 回 mock、真實/測試走 AI。
- 兩者疊加效果：demo 帳號開箱即見「seed 資料 + 穩定 mock 的 AI 結果」可完整示範；真實帳號用「自己的資料 + 真實 AI」。

## Web Push 推播總機制（Phase 5）

PurePaw 以標準 Web Push（VAPID + Service Worker）對使用者裝置送系統通知，分兩類：**食安警報**與**用藥/美容提醒**。共同流程如下。

### 訂閱與退訂（設定頁 → API → DB）

```
設定頁通知設定 tab（PushSettings）切開關
  ├─ 開啟：能力偵測 → Notification.requestPermission() → 註冊 /sw.js
  │       → pushManager.subscribe（用 NEXT_PUBLIC_VAPID_PUBLIC_KEY）
  │       → POST /api/push/subscribe（帶 endpoint + keys + 兩開關）
  │            └─ upsert by endpoint（唯一鍵），存 p256dh/auth 與兩偏好開關
  └─ 關閉：兩類皆關 → 退訂瀏覽器 + DELETE/POST /api/push/unsubscribe（依 endpoint 刪 DB）
          僅關一類 → 只更新後端對應開關（仍保留訂閱）
```

- **狀態一律以後端 GET 為準**：設定頁載入呼叫 `GET /api/push/subscribe` 取 `{ subscribed, foodAlertEnabled, reminderEnabled }`，避免前端與 DB 不一致。
- **iOS 限制**：iOS Web Push 需先「加入主畫面」(standalone)。設定頁偵測非 standalone 時顯示「請先加入主畫面」引導，不顯示假 toggle。`public/manifest.webmanifest` + layout 的 `appleWebApp` 是此前置條件。
- **權限被拒 / 瀏覽器不支援**：給對應提示，不中斷其餘功能。

### 送推 helper（`src/lib/push.ts`）

- `sendPush(subscription, payload)`：送單筆。**失效訂閱（statusCode 410 Gone / 404 Not Found）自動從 DB 刪除該 endpoint**；其他錯誤僅記 log 不刪（可能是暫時性問題）。
- `sendPushToUser(userId, payload, kind)`：依 `kind`（`foodAlert` / `reminder`）過濾對應開關（`foodAlertEnabled` / `reminderEnabled`）後送該使用者全部訂閱，回成功送達筆數。
- `sendInBatches(items, worker)`：**每批上限 50 筆（`PUSH_BATCH_SIZE`），逐批 `Promise.allSettled` 並行**。單一目標失敗（含其內部 `sendPush` 拋錯）不影響同批其他目標；各 worker 回傳「成功送達筆數」，最後加總。serverless 環境避免一次開太多外送連線。
- **VAPID 私鑰只在本檔使用**，採延後設定（首次送推才讀 env），避免 build 期 import 即報錯；缺金鑰時於實際送推才丟 `VAPID keys are not configured`。

### Service Worker（`public/sw.js`）

純 JS、不經 Next 編譯，由根路徑 `/sw.js` 提供：

- `install` → `skipWaiting()`；`activate` → `clients.claim()`，讓新版 SW 即時接管所有頁面。
- `push`：解析 payload 顯示系統通知；payload 非 JSON 時退回純文字當內文。**個人化頭條**（`data.headline === true` 或 `data.priority === 'high'`）時改用 `requireInteraction`（需手動關閉）、`renotify`（同 tag 覆寫時重新提醒）、`vibrate`，顯示更顯眼。
- `notificationclick`：聚焦既有同源視窗並 `navigate` 到 `data.url`，否則開新視窗，預設 `/news`。

### demo 推播：走真實觸發、內容 mock（frank 拍板）

demo 帳號的推播**改成「也走真實觸發、但內容 mock」**，不再是 no-op 排除：

- **訂閱/退訂與真實帳號完全相同**：demo 也真的把訂閱寫進（測試）DB，OS 才收得到推播；退訂也真的刪 DB。
- **唯一差異在「送出的內容」**：`sendPushToUser()` 發送前以 `isDemoUserId(userId)`（只比對 `userId === 'demo-user'`）判斷，是 demo 就把 payload 換成該 kind 的固定 `DEMO_MOCK_PAYLOAD`（範例食安 / 範例提醒，結構與正常 payload 一致），不外洩真實食安內容、回應穩定可重現。
- **一處統一**：所有觸發流程（食安、提醒 cron）對 demo 一律送 mock，呼叫端無需各自處理；食安觸發查詢訂閱者時**不再排除 demo**（demo 納入發送對象，內容由 push.ts 換 mock）。

> 注意：此處的 demo「走真實流程、只換內容」是在**測試環境**（連 `dev.db`）內成立。正式站（Vercel 連 Turso）**不開 demo 登入口**，demo 完全不會出現在正式環境（見本檔末「測試 / 正式環境資料策略」）。

## 食安警報觸發推播機制（`/api/news/crawl` → `triggerFoodAlertPush()`，Phase 5）

快訊 AI 生成（`news/crawl`）寫入 `NewsArticle` 後，**接著觸發食安警報推播**（以 try/catch 隔離，推播失敗不讓整個 crawl 回錯）。

### 觸發條件與去重

```
triggerFoodAlertPush()
  ├─ 取候選快訊：category='food_safety' AND isUrgent=true AND foodAlertPushedAt IS NULL
  │    （涵蓋本批新生成 + 任何前次漏推的）
  ├─ 取訂閱者：PushSubscription where foodAlertEnabled=true（含 demo），去重成 userId 清單
  ├─ 預載每位訂閱者「正在使用的產品關鍵詞」（見個人化頭條）
  ├─ 對每篇快訊 × 每位訂閱者：sendInBatches 分批並行送出
  └─ 每篇推完（即使 0 訂閱）update foodAlertPushedAt = now()
       └─ 同篇只推一次：cron 重跑 / 手動 POST 皆安全，不會重複推
```

- 「食安警報」沿用既有 `category === 'food_safety'`，「緊急」沿用既有 `isUrgent`，未另加旗標。
- `foodAlertPushedAt`（非 null = 已推）是去重關鍵；候選查詢只取尚未推的，配合推完即標記，達成「每篇只推一次」。

### 個人化頭條（命中飼主使用中的產品）

- AI 生成食安警報時一併輸出 `affectedBrands`（涉及的廠商/品牌/產品關鍵詞 JSON array；僅食安警報需填，通泛成分警示或其他分類回 `[]`）。經 `sanitizeAffectedBrands()` 只收非空字串、去重後，僅 `food_safety` 且有品牌才以 `JSON.stringify` 存入 `NewsArticle.affectedBrands`。
- 預先載入每位訂閱者「正在使用的產品關鍵詞集合」：`PetProduct where isActive=true` 且該毛孩屬其 owner（`pet.userId`）或 co_owner（`PetMember`），取 `Product.name / brand / variant` 正規化（小寫 + NFKC + 去標點空白，與既有標題去重規則一致）。
- `brandsHitProducts()`：警報 `affectedBrands` ∩ 使用者產品關鍵詞，採雙向子字串包含（長度下限 2 避免偶然命中）。
  - **命中** → `headlineFoodAlertPayload`：標題前綴「⚠️ 你的毛孩正在使用的產品」，payload 帶 `priority:'high'` / `headline:true`（SW 顯示更顯眼）。
  - **未命中** → `normalFoodAlertPayload`：標題「⚠️ 食安警報」。
- payload `data.url = /news?article=<id>` 導向該快訊；`tag = food-alert-<id>` 避免通知堆疊。
- 命中數於 `sendInBatches` 的 worker 內依「實際送達筆數」累加（語意與序列版一致）。

### 統計回應

`news/crawl` 回應 JSON 加上 `push: { articles, recipients, headlines }` 統計，便於驗證觸發結果。

> 個人化比對採關鍵詞子字串啟發式，可能漏判（品牌縮寫/別名）或偶發誤判，屬可接受的 MVP 取捨；日後可引入品牌正規化字典提升精準度。

## 用藥/美容提醒機制（`/api/reminders/check` cron，Phase 5）

每日 cron 掃出到期的用藥/美容提醒並送推，支援**一次性**與**週期性**兩種。

### 設定提醒（Modal `ReminderSetter`）

- 用藥看診 / 洗澡美容兩個 Modal 共用 `ReminderSetter`（取代原本 `alert('提醒功能即將推出')`）：提醒日期 + 提醒頻率（一次性 / 週期快捷）。
- 頻率寫入紀錄的 `reminderIntervalDays`（`null`=一次性、`>0`=每 N 天循環），到期日寫 `nextReminder`，隨既有 POST（`/api/medication-record`、`/api/grooming-record`）一併送出（少一次往返）。週期快捷：用藥每月 30 / 每季 90 / 每年 365；美容每月 30 / 每兩月 60 / 每季 90。

### cron 流程與授權

```
GET（Vercel Cron）/ POST（手動）/api/reminders/check
  ├─ 授權：Authorization: Bearer <CRON_SECRET>（未設定一律 401，比照 news/crawl）
  ├─ 算「台灣今天結束」對應的 UTC 上界（taiwanTodayEndUtc）
  ├─ 查 MedicationRecord / GroomingRecord：nextReminder != null AND nextReminder <= 上界
  ├─ 每筆 → 取該毛孩 owner（Pet.userId）+ co_owner（PetMember）去重後的 userId
  │       → sendInBatches 分批並行 sendPushToUser(userId, payload, 'reminder')
  │            （helper 內已過濾 reminderEnabled；demo 自動換 mock）
  └─ 推完更新 nextReminder：一次性 → null；週期性 → 順延一個週期
```

- payload 導向 `/log`；用藥 `tag = reminder-med-<id>`、美容 `tag = reminder-grooming-<id>`。
- 排程：`vercel.json` 設每日 00:00 UTC（台灣 08:00，早上提醒當日待辦）。

### 台灣時區到期判定（重點）

- Vercel cron 以 UTC 執行；`0 0 * * *` = UTC 00:00 = 台灣 08:00。
- `nextReminder` 由 date input 的 `'YYYY-MM-DD'` 經 route `new Date(str)` 存成 **UTC 午夜**（例 `'2026-06-10'` → `2026-06-10T00:00:00Z`）。
- `taiwanTodayEndUtc(now)`：把 now 推進 8 小時取其 UTC 日期當「台灣今天」，再算出「台灣今天 23:59:59.999」對應的 UTC 時間點當查詢**上界**（`lte`）。
- 用上界 `lte` 而非單日區間，可**同時涵蓋「今天到期」與「先前漏推（已過期）」**的提醒——cron 漏跑一天也能補上。

### 一次性 vs 週期性

| | `reminderIntervalDays` | 到期推播後（`computeNextReminder`） |
|---|---|---|
| 一次性 | `null` | `nextReminder = null`（不再提醒） |
| 週期性 | `N (>0)` | `nextReminder += N` 天；若早已過期多次，連推到未來，避免下一次 cron 又判定到期重推 |

- demo：`sendPushToUser` 內對 demo userId 自動換 mock，cron 不需特別處理；`nextReminder` 仍照常更新。

## 快訊 AI 生成機制（`/api/news/crawl`，Phase 4）

`/news` 三分類（食安 food_safety / 危險禁忌 danger / 健康知識 health）的內容由 AI 定期生成寫入 `NewsArticle`，不再是空 DB 或靜態示範。

### 觸發與授權

- **同一套 `handle()`，同時 export `GET` 與 `POST`**：Vercel Cron 以 **GET** 觸發排程 endpoint（原本只有 POST，cron 會打不到），因此抽出共用邏輯讓兩個方法都能用。GET 給 Cron 排程、POST 給手動觸發，兩者走同一套授權。
- **授權**：以 `Authorization: Bearer <CRON_SECRET>` 比對；`CRON_SECRET` 未設定時一律回 401（不放行），避免被任意呼叫。
- **排程**：`vercel.json` 設定每日 02:00 UTC（台灣 10:00），正式站由 Vercel 自動帶 Bearer。

### 生成與寫入流程

```
GET/POST /api/news/crawl（授權通過）
  └─ claude-sonnet-4-6 一次生成三類文章（prompt 附 VET_REFERENCE_SCOPE）
       ├─ stripCodeFence()：先剝除 AI 偶爾包的 ```json fence 再 parse（降低 502）
       ├─ isValidArticle()：過濾髒資料
       ├─ 去重：近 7 天「同分類同標題」不重複寫入
       └─ 寫入 NewsArticle → 回 { created, skipped }
```

- 錯誤分流：AI 格式錯誤（`ParseError`）→ 502；其他例外 → 500。
- `category="food_safety"` 且帶 `isUrgent` 旗標的快訊可作為未來食安警報推播來源。

## 症狀詳情頁 AI 建議機制（`/api/symptoms/advice`，Phase 4）

症狀詳情頁（`/symptoms/[type]`）依該毛孩、該症狀類型的紀錄，生成 AI 的「可能原因 / 建議做法」，並以 `AIInsight` 快取避免重複打 AI。

### 生成流程

```
GET /api/symptoms/advice?petId=&symptomType=（&refresh=1）
  ├─ auth() + requirePetAccess（先驗權再打 AI）
  ├─ 撈該毛孩該症狀類型近 30 筆紀錄；無紀錄 → { advice: null }（不打 AI）
  └─ 算 dataHash（見下）→ 查 AIInsight 快取
       ├─ 雜湊相同且非 refresh → 直接回快取（cached: true，不打 AI）
       └─ 雜湊不同或 refresh=1 → claude-sonnet-4-6 生成 → 寫入新一列 AIInsight
```

- prompt 注入毛孩資料 + 歷次紀錄（由舊到新呈現趨勢），附 `VET_REFERENCE_SCOPE`，明確要求「非醫療診斷、嚴重請立即就醫」語氣。
- 要求回傳 JSON `{ possibleCauses[], recommendedActions[] }`；解析失敗時退化為純文字塞進可能原因仍可顯示。

### 快取雜湊（沿用 `AIInsight`，不新增資料表）

- `dataHash` = 對 `petId + symptomType + 各紀錄(id/severity/notes/createdAt)` 算 sha1，任何新增/刪除/編輯紀錄都會改變雜湊。
- 存入：`suspectedTriggers` 欄位塞 `["__hash__:<hash>"]`（此欄位本功能未使用）；`rationale` 存「可能原因」整段、`recommendedActions` 存建議陣列；`symptomType` 為該症狀類型。
- GET 時撈該 `(petId, symptomType)` 最新一列比對雜湊即可判斷快取是否有效。效果：同一症狀類型在沒有新紀錄時，反覆進頁面只打一次 AI。

### 前端（`symptoms/[type]/page.tsx`）

- 「AI 觀察建議」卡片置於統計與記錄列表之間，分「可能原因 / 建議做法」兩段，底部固定一行免責聲明；提供「重新生成」按鈕（帶 `refresh=1`）。
- 狀態：載入中（「AI 分析中…」）、失敗（紅字 + 重試鈕）、無建議（「暫無 AI 建議」）、無紀錄則整張卡不顯示。
- **順帶修正抓錯毛孩 bug**：原本用 `fetch('/api/pets')` 取 `pets[0]`（最舊寵物）→ 改讀 `localStorage['drpet_currentPetId']` + `storage` 事件同步，對齊全站「當前毛孩」做法。

## 日誌月摘要 AI 解讀機制（`/api/month-summary`，Phase 4）

`MonthHealthOverview` 統計數字下方，加入一段依當月 `DailyHealthLog` 統計生成的「AI 健康解讀」白話摘要。

### 後端聚合 + 生成

```
GET /api/month-summary?petId=&yearMonth=YYYY-MM
  ├─ auth() + requirePetAccess（先驗權再打 AI）
  ├─ 撈當月 DailyHealthLog → 後端自行聚合（與前端 MonthHealthOverview 一致的正常值白名單邏輯）
  │    算出：有日誌天數 / 異常天數 / 良好天數 / 各指標分佈（活力/食慾/飲水/排便/泌尿異常/症狀觀察部位）
  ├─ logs.length === 0 → { summary: null }（前端不顯示）
  └─ claude-sonnet-4-6 生成（prompt 附 VET_REFERENCE_SCOPE、非診斷語氣、3~5 句約 120 字白話、不用 markdown）
```

### 程序內快取（不新增 Prisma model）

- `summaryCache = new Map<string, string>()`，鍵為 `petId|yearMonth|statsHash`。
- `statsHash` = 對「聚合後統計物件」做 sha1 取前 16 碼：統計一變動 hash 就變、舊鍵自然失效；統計不變直接回快取（`cached: true`）不重打 AI。
- **快取上限保護**：`SUMMARY_CACHE_MAX = 200`，插入超過上限時刪除 Map 最舊一筆（插入序近似 LRU）；命中讀取時也重新插入以更新近因，避免熱門月份被當最舊淘汰、避免快取無界成長。
- 適用單機 / Serverless 暖實例；冷啟動會重算一次，仍受下面客戶端去重保護。

### 前端輪詢不重打（`MonthHealthOverview.tsx`）

- 以 `aiStatsSig`（由 `monthLogs` 各觀察欄位組成的輕量簽章）+ `lastAiSigRef` 比對：`refreshKey`（20–30 秒輪詢）變動但統計沒變 → 簽章相同 → **直接 return 不發 fetch**；只有當月健康資料實質改變才重打。
- 雙層保護：即使客戶端送出 fetch，後端 statsHash 快取也會避免重複打 AI。
- UI 放在月健康摘要卡內「各指標每月分佈」區塊下方，附「僅供參考，非醫療診斷」免責句；載入中顯示 spinner、失敗顯示「暫時無法產生」並重置簽章以便下次重試；無資料不渲染該段。

## 換食計畫 AI 機制 + 結束計畫（`/api/switch-plan-ai`，Phase 4）

換食計畫「計畫進行中」畫面（`DietPlanActive`）的三區塊改吃 AI 結果，並新增「結束計畫」入口。

### AI 換食建議生成

```
POST /api/switch-plan-ai  body: { petId, dayCount }（換食第幾天，1 起算、上限 14）
  ├─ auth() + requirePetAccess（先驗權再打 AI）
  ├─ 取該毛孩近 7 日 DailyHealthLog（排便型態/排便細節/皮膚毛髮/消化/胃口/精神，parseJson 安全讀）
  ├─ 近 7 日日誌 < 3 天 → degradedResult()（線性排程比例 + 身體監控標「尚無足夠日誌」+ 待觀察，degraded:true，不打 AI）
  └─ claude-sonnet-4-6 生成（prompt 附 VET_REFERENCE_SCOPE）→ 數值驗證 → 回三區塊結果
```

輸出 `SwitchPlanResult` 對應三區塊：

| 欄位 | 內容 |
|------|------|
| `schedule` | 今日建議比例（新:舊）+ `label` + 進度條百分比 |
| `bodyMetric` | 大便分數（0–7）、狀態、抓癢頻率（次/日）、趨勢、是否惡化 |
| `verdict` | 晉升/淘汰建議（`suitable` / `monitor` / `discard` + 文字提示） |

### AI 數值驗證（不直接信任 AI 回傳）

組裝結果前套用三個驗證函式，髒值走正規化或降級：

- `validateSchedule`：`newPct`/`oldPct` 非有限數字 → 走線性降級；否則 `newPct` 夾 0–100 後 `oldPct = 100 − newPct`（自然修正「和不為 100」），label 缺漏自動生成。
- `validateBodyMetric`：`stoolScore` 夾 0–7、`scratchPerDay` ≥0、非數字補 0；`scratchWorsening` 非布林補 false；狀態字串缺漏補佔位。
- `validateVerdict`：`status` 限三個合法 enum，否則降級為 `monitor`；message 缺漏補佔位。

### 前端（`DietSwitchPlan.tsx`）

- 「排程比例 / 身體特徵監控」兩區塊改吃 AI；AI 載入中／失敗回退既有 mock（`recommendedRatio()` / `MOCK_BODY_METRIC`），維持設計圖長相不破。
- 新增「晉升/淘汰建議」區塊：身體特徵監控下方顯示 AI `verdict`（綠=適應良好 / 紅=建議淘汰 / 米=持續觀察）。排程區標題列加 AI 狀態（載入中 spinner、失敗/資料不足可點重試）。
- **當前測試商品仍為 mock**（換食商品來源尚未串接）。
- **「結束計畫」按鈕**：畫面底部行動鈕下方新增文字入口，點下展開確認框（確認 + 取消，避免誤按）；確認後呼叫 `endPlan` 清除 localStorage（`drpet_hasPlan` / `drpet_planStart`），回未啟動畫面。與「晉升日常飲食 / 淘汰並更換」區隔：單純臨時中止、不視為有結論的結束。

## 飲食頁「添加項目」AI 搜尋機制（`AddItemModal`，Phase 4）

## 日誌頁機制（`/diary`）

### 月/週曆雙模式切換

日誌頁頂部有「月曆頁面 / 週曆頁面」segmented control，`calTab` state 控制：

| 模式 | 月曆（預設） | 週曆 |
|------|------------|------|
| 日曆元件 | `MonthCalendar` | `WeekCalendar` |
| 日曆下方 | `MonthHealthOverview`（唯讀） | `HealthLogSection`（可編輯） |

**月曆模式**：點擊日期後，`MonthCalendar` 透過 `onDateSelect` 回調更新父層 `monthSelectedDate`，`MonthHealthOverview` 隨即載入該日 `DailyHealthLog` 並以 pill 形式顯示各健康指標（活力/食慾/飲水/排便/泌尿），並列出有觀察紀錄的身體部位。同時顯示本月已記錄天數及記錄完整度進度條。

**週曆模式**：顯示 `HealthLogSection`，內含 SmartMemo AI 隨記 + DailyChecklist + DietStatusCard + 全部 13 張健康卡片，提供完整的當日健康記錄編輯功能。

### 日曆圓點資料源統一（`/api/diary-dates`）

月曆與週曆上「有紀錄圓點」與「已紀錄 X 天」過去只看 `ProductUsage`，會漏掉其他種類的紀錄。現改由 `GET /api/diary-dates?petId=&yearMonth=YYYY-MM` 在後端**聚合 7 種紀錄來源**，回傳當月「有任何一種紀錄」的不重複日期清單（`YYYY-MM-DD`）：

| 來源 model | 日期欄位型態 | 判斷方式 |
|------------|------------|----------|
| `DailyHealthLog` | String（`YYYY-MM-DD`） | 前綴比對 `startsWith('YYYY-MM-')` |
| `HealthMetric` | String | 同上 |
| `MedicationRecord` | String | 同上 |
| `GroomingRecord` | String | 同上 |
| `MeasurementRecord` | String | 同上 |
| `ProductUsage` | DateTime | `date` 落在當月 UTC 區間 `[monthStart, monthEnd)` |
| `SymptomEntry` | DateTime | `createdAt` 落在當月 UTC 區間 |

七個查詢以 `Promise.all` 並行，結果丟進 `Set` 去重後排序回傳。

`/diary` 頁面把回傳的日期放進 `recordedDates`（`Set<string>`），**月曆與週曆共用同一份**：用於畫圓點（`recordedDates.has(key)`）、月曆模式「已記錄 X 天」徽章（`recordedDates.size`）。週曆若跨月（該週橫跨兩個月份）會同時查兩個月份再合併。快捷 Modal 儲存後（`handleModalSaved`）會把當天加進 `recordedDates` 並觸發重新聚合，讓新紀錄立刻在圓點上反映。

### 週曆日期選取連動 + 上一週/下一週切換

週曆模式的 `WeekCalendar`（`/diary` 內建元件）改為**受控元件**：選取日期由父層 `selectedDate` 持有，週曆只負責顯示與上拋事件。

```
WeekCalendar 點選某日
  └─ onSelectDate(key) → setSelectedDate(...)   ← 直接同步父層 selectedDate
       └─ selectedDate 同時驅動：
            ├─ 區段標題（「今日 / M/D 健康紀錄」）
            └─ HealthLogSection（讀寫該日 DailyHealthLog）
```

所有跟「某一天」相關的編輯區塊都吃同一個 `selectedDate`，切換日期時健康卡片會一起換到那天的資料。

**上一週 / 下一週切換**：週曆顯示的週由 `weekStart`（該週週日）決定，`goPrevWeek` / `goNextWeek` 把 `weekStart` ±7 天即可切換顯示週；換週時上拋的 `selectedDate` **維持不變**，僅切換可見的那一週。

**移除週曆內重複的 DayDetail**：舊版週曆內部還有一塊 `DayDetail` 空區塊與下方 `HealthLogSection` 功能重疊，現已移除；週曆選取的日期直接驅動 `HealthLogSection`，不再有重複面板。（`DayDetail` 仍保留在月曆模式中，點日期時展開該日紀錄。）

### HealthLogSection 獨立元件與效能優化

**效能優化原因**：原本 `healthLog` state 位於 1600+ 行的 `DiaryPage` 中，任何卡片點擊都會觸發整頁重繪（月曆、AI 推薦、換食計畫等），造成明顯延遲。抽出後，卡片點擊只重繪 `HealthLogSection`。

### DailyHealthLog debounce 自動儲存流程

使用者在任一健康卡片上操作（選擇食慾狀態、輸入飲水量等）後，不需手動按儲存按鈕，系統會自動儲存：

```
使用者操作任一健康卡片的 onChange
  └─ 前端更新本地 state
       └─ 觸發 1000ms debounce 計時器（新操作會重置計時）
            └─ 計時結束 → POST /api/daily-health-log（upsert）
                 ├─ 當日已有紀錄 → 更新對應欄位
                 └─ 當日無紀錄 → 建立新 DailyHealthLog
```

每次 upsert 送出完整的當日健康日誌 payload，不做局部欄位更新，以避免欄位覆蓋衝突。debounce 1000ms 的設計在使用者快速切換選項時只觸發最後一次儲存，減少 API 呼叫次數。

### 月曆總覽聚合機制（MonthHealthOverview）

`GET /api/daily-health-log?petId=&yearMonth=YYYY-MM` 一次回傳整月所有 `DailyHealthLog` 記錄（`date BETWEEN YYYY-MM-01 AND YYYY-MM-31`）。

`MonthHealthOverview` 元件接收整月資料後，在前端聚合。最上方先顯示一行白話摘要（例：「本月 12 天有紀錄，其中 8 天有健康日誌、6 天狀況良好，2 天有異常觀察」），再列出統計數字與各指標分佈。

#### 正常值白名單與「異常」判斷

過去把「任意多選欄位有值」一律當成異常，導致情緒選「平靜放鬆」也被算成異常。現改為**每個觀察欄位各有一份「正常值白名單」**，只有出現「不在白名單」的值才算異常觀察：

- **單選欄位**：活力（精神飽滿/活動意願高）、食慾（胃口極佳/食慾正常）、飲水（飲水正常）、排便（正常成形/羊便便(硬)）、泌尿（尿量正常）——值不在各自白名單即視為異常。
- **多選欄位**（`abnormalMultiValues()`）：情緒行為的正常值白名單為「平靜放鬆／活潑好動」；皮膚毛髮/眼耳/牙齒口腔/消化/呼吸/神經溫控/生殖分泌等卡片的所有選項都是異常徵兆，白名單為空集合（**有值即異常**）。函式回傳該欄位中「非白名單」的值清單，清單非空代表該欄位當日有異常觀察。

#### 三個統計數字「全部以 DailyHealthLog 同源計算」

避免「只有飲食紀錄的日子」被誤算成健康良好：

| 數字 | 計算方式 |
|------|----------|
| 健康日誌天數 | 有 `DailyHealthLog` 的不重複天數（`healthLogDays`） |
| 有異常 | 含任何非白名單觀察值的天數（`hasAbnormality()` 逐日判斷） |
| 健康良好 | `健康日誌天數 − 有異常天數`，必不為負（同源相減，不再各自獨立計算） |

#### 「已記錄 X / 當月天數」徽章與圓點同義

頂部徽章與摘要句的「已記錄天數」**改吃父層傳入的 `recordedCount`**（即 `/api/diary-dates` 聚合的本月「任何紀錄來源」不重複天數，與月曆圓點完全同義），不再只看健康日誌。未傳入時退回 `healthLogDays` 避免顯示 0。

#### 各指標月份分佈

- 用 `topValue()` 取各指標出現頻率最高的值作為「本月最常見狀態」（舊版摘要，保留向下相容）。
- 用 `countByValue()` 計算各指標每個值出現的天數，分小節顯示分佈：活力指數、食慾、飲水、排便（各類型 N 天）、泌尿異常（排除「尿量正常」只顯示異常）、症狀觀察（各身體部位有**異常觀察**的天數，正常值如情緒「平靜放鬆」不計）。
- `MetricSection` 子元件統一渲染各指標分佈，以「值 N天」pill 形式顯示，搭配顏色函式（綠/黃/紅）標示健康狀態。

同時接收 `date`（單日日期）單獨 fetch 單日摘要，以 pill 形式顯示活力/食慾/飲水/排便/泌尿，以及該日有「異常觀察」的部位（同樣套用正常值白名單）。

## 共同飼主存取控制機制

毛孩可以同時被「主人（owner）」與「共同飼主（co_owner）」存取。為避免任何人帶著別人的 `petId` 就讀寫到別人的毛孩資料，所有寵物相關 API 都先經過 `src/lib/petAccess.ts` 的權限把關才動資料。

### 雙重判定（`requirePetAccess(petId, userId)`）

判定順序如下，回傳結果為 `{ ok:true, role:'owner'|'co_owner' }` 或 `{ ok:false, status }`：

```
requirePetAccess(petId, userId)
  ├─ userId 為空 → 401（未登入）
  ├─ 查 Pet：不存在 → 404
  ├─ Pet.userId === userId → owner    ← 先看 Pet 本身的主人欄位
  │    （涵蓋既有 owner / demo 帳號，即使資料庫沒有對應 PetMember 也不會被擋）
  └─ 否則查 PetMember（petId + userId 複合鍵）
       ├─ 存在 → 回該 member 的 role（owner / co_owner）
       └─ 不存在 → 403（非此毛孩的成員）
```

「先看 `Pet.userId`、再查 `PetMember`」的雙重判定是為了相容歷史資料：早期建立、或 demo 帳號的毛孩可能只有 `Pet.userId`、沒有 `PetMember` 紀錄，若只認 `PetMember` 會把這些 owner 全部誤擋成 403。

### 由紀錄反查（`requirePetAccessByRecord(model, recordId, userId)`）

有 6 支 route 的網址路徑帶的是「某筆紀錄的 id」而非 `petId`（例如刪除某筆症狀、某筆飲食使用）。這類 route 改用 `requirePetAccessByRecord`：先用 recordId 反查它所屬的 `petId`，再走上面的 `requirePetAccess`。

| model | 反查的關聯欄位 | 使用的 route |
|-------|--------------|-------------|
| `symptomEntry` | `petId` | `symptoms/[id]`（GET/DELETE） |
| `productUsage` | `petId` | `usages/[id]`（PUT/DELETE） |
| `petProduct` | `petId` | `pet-products/[id]`（PATCH/DELETE） |
| `instantAnalysis` | `petId` | `instant-analyze/[id]`（DELETE） |
| `dailyMealPlan` | `petId` | `meal-plans/[id]/items`（POST/DELETE） |
| `communityRec` | `forPetId`（特例映射） | `community/dismiss`（POST） |
| `weeklyTask` | `petId` | `tasks`（PATCH，IDOR 補修） |

紀錄不存在 → 404；成功時連 `petId` 一起回傳，呼叫端不必再查一次。`CommunityRec` 的所屬毛孩欄位叫 `forPetId`（不是 `petId`），已特別映射處理。

### 各類 API 的權限分級

所有寵物相關 route 統一模式：`auth()` 取 session → `requirePetAccess`／`requirePetAccessByRecord`（`userId` 取 `session?.user?.id ?? ''`）→ 失敗時直接回對應的 `access.status`（401/403/404）。AI route 一律把權限檢查放在呼叫 Anthropic **之前**，避免未授權者也能耗用 AI token。

| 分級 | 允許角色 | 範例 route |
|------|---------|-----------|
| 讀（R） | owner + co_owner | 各種 GET（健康日誌、日曆、量測、用藥、美容、症狀、飲食使用…） |
| 寫（W） | owner + co_owner | 各種 POST/PUT/PATCH（含 AI 寫入：diary-parse、analyze、recommend、chat…） |
| 刪毛孩 | **owner-only** | `pets/[id]` DELETE（`role !== 'owner'` → 403） |
| 邀請管理 | **owner-only** | 共同飼主邀請的建立／管理 |

此外，部分 GET 的 `petId` 由「可選」改為「**必填**」（缺少即 400）：`symptoms`、`usages`、`documents`、`tasks` 四支。前端既有呼叫端都已帶 `petId`，無需修改。

### `/api/pets` 共享查詢

`GET /api/pets` 的 `where` 由原本只看 `{ userId }`，改為 `{ OR: [{ userId }, { members: { some: { userId } } }] }`，讓共同飼主（在 `PetMember` 裡有紀錄者）也能在毛孩清單看到被分享給自己的毛孩。排序與回傳形狀不變（OR + relation filter 不會展開出重複資料列），未登入（demo）仍回全部。

### owner membership 與 backfill

- **建立毛孩即建 owner member**：`POST /api/pets` 建立毛孩時，同時建立一筆 `role:'owner'` 的 `PetMember`，讓新資料一開始就同時具備 `Pet.userId` 與 `PetMember` 兩種歸屬。
- **seed 補 demo owner member**：`prisma/seed.ts` 在 demo 毛孩建立後 upsert 一筆 owner `PetMember`（冪等保險；雙重判定其實已涵蓋）。
- **冪等 backfill migration**：`prisma/migrations/20260604000000_backfill_owner_membership/migration.sql` 以 `INSERT ... SELECT ... WHERE NOT EXISTS` 為「有 `Pet.userId` 但缺 `PetMember`」的歷史毛孩補建 owner membership（`joinedAt` 沿用 `Pet.createdAt`）。**目前僅在本機 `dev.db` 套用**，正式 Turso 留待 DevOps 部署時與其他落後 migration 一起處理；部署順序為「**先跑 backfill → 再上權限程式碼**」（雙重判定已大幅降低先上碼導致 owner 全 403 的風險，但仍以此順序為準）。

### community/trigger 改為進程內呼叫

產品反應（`reactions`）寫入後要連動產生「社群推薦」。原本 `reactions` POST 是用 HTTP self-call 去打 `community/trigger`，但 self-call 沒有帶 session cookie，一旦對 trigger 套上權限就會被自己 401 擋掉。

修法：把推薦產生邏輯抽到 `src/lib/community.ts` 的 `processReactionForCommunity(...)`，`reactions` POST 改在**進程內直接呼叫**（`void processReactionForCommunity(...)`，fire-and-forget、吞錯不拋例外），權限改由 `reactions` 一處把關。`community/trigger` route 仍保留為對外端點，並補上 `auth()` + `requirePetAccess` 後呼叫同一函式。

## 共享資料輪詢同步機制（`usePollingRefresh`）

共同飼主場景下，多人可能同時操作同一隻毛孩的資料。為了讓 A 端的變更能在 B 端看到，在不引入 SWR / React Query 的前提下，用 `src/hooks/usePollingRefresh.ts` 做輕量輪詢同步。

### Hook 行為（`usePollingRefresh(refresh, intervalMs = 25000)`）

- 每 `intervalMs`（預設 25 秒）呼叫一次傳入的 `refresh`（即頁面既有的載入函式）。
- **分頁切回可見**（`visibilitychange` → visible）→ 立即 `refresh` 並重啟輪詢；**分頁隱藏** → 暫停輪詢（清掉 interval），背景分頁不浪費請求。
- **視窗重新取得焦點**（window `focus`）→ 立即 `refresh`。
- 用 `refreshRef`（useRef）保存最新的 `refresh`，effect 相依只有 `intervalMs`，因此 `refresh` 參考改變也不會重建計時器/監聽器；呼叫端仍應以 `useCallback` 穩定 `refresh`。
- 起始時若分頁已是隱藏狀態則先不啟動，待切回可見再啟動；卸載時清掉 interval 與兩個 listener。

### 套用頁面與刻意跳過的部分

| 頁面 | 輪詢重抓的內容 |
|------|--------------|
| 首頁（`src/app/page.tsx`） | 毛孩列表（`/api/pets`）+ 當前毛孩當日健康指標/餐數（`/api/health-metrics`、`/api/usages`）。`fetchPets` 改用函式式更新當前毛孩，避免重抓時把使用者剛切換的當前毛孩重設掉 |
| 日誌（`src/app/diary/page.tsx`） | 月曆/週曆「有紀錄圓點」（`recordedDates`）+ 月健康總覽（`MonthHealthOverview`，透過 `refreshKey` prop 連動重抓） |
| 飲食（`src/app/diet/page.tsx`） | 今日配餐計畫（`/api/meal-plans`）；`fetchPlan` 加 `silent` 參數，輪詢時不顯示整頁 spinner 以免閃爍 |
| 寵物詳情（`src/app/pet/[id]/page.tsx`） | 毛孩資料（`/api/pets/[id]`）；**編輯中（`editing`）時跳過輪詢**，避免覆寫尚未儲存的表單 |

**刻意不輪詢**：

- **日誌週曆模式的 `HealthLogSection`（當日健康編輯區）不納入輪詢**——它是使用者即時編輯、debounce 自動存檔的表單，若被伺服器資料覆寫會清掉尚未送出的輸入。共享同步的價值在「唯讀彙整」（圓點、月總覽），故只刷新那些。
- 飲食頁的寵物基本資訊（名稱/物種/過敏等極少變動）不輪詢，只刷新會頻繁變動的今日配餐。

`MonthHealthOverview` 內部「整月 logs」與「單日 log」兩個 fetch 各用一個簽名 ref（`lastFetchSigRef` / `lastDaySigRef`）：只有 `petId`/`yearMonth`（或 `date`）真的改變才顯示載入狀態，純 `refreshKey` 變動（輪詢）時靜默更新，避免每 25 秒閃一次 spinner。

## 共同飼主 Email 邀請機制

毛孩主人（owner）可以邀請其他人成為「共同飼主」，一起檢視與記錄毛孩健康。邀請現在會「真的寄出一封 Email」。

### 寄信模組（`src/lib/email.ts`）

- 使用 nodemailer 透過 Gmail SMTP 寄信，認證帳號為系統專用 Gmail（環境變數 `GMAIL_USER` / `GMAIL_APP_PASSWORD`）。
- 寄件人顯示名稱固定為「無敏毛孩 PurePaw」。
- 對外提供兩個函式：`sendEmail()`（通用寄信）與 `sendInviteEmail()`（組裝邀請信主旨與 HTML 後寄出）。
- 邀請信為內嵌品牌色 `#C4714A` 的 HTML 模板，含「接受邀請」按鈕、純文字備援連結、7 天有效提醒。
- 凡是會放進 HTML 的使用者可控字串（毛孩名、邀請人名、連結）都先經過 `escapeHtml()` 跳脫，避免破版或 HTML 注入。
- transporter 與通過驗證的寄件地址會被快取，避免重複讀取環境變數。
- 設計上為未來可抽換：若改用 Resend 或自有網域 `noreply@`，只需替換 `email.ts` 內部實作，呼叫端不必更動。

### 建立邀請 → 寄信 → emailSent → QR Code 備援流程

```
設定頁 owner 輸入對方 Email 送出
  └─ POST /api/pets/[id]/invitations
       ├─ 驗證權限（必須為該毛孩的 owner）
       ├─ 確認對方尚未是成員；若有舊的 pending 邀請先設為 expired
       ├─ 建立 PetInvitation（含 token，7 天後到期）
       ├─ 組裝 inviteUrl = `${baseUrl}/invite/${token}`
       │    └─ baseUrl 取自 NEXTAUTH_URL / AUTH_URL；皆缺失時 console.warn 提醒（連結會失效）
       ├─ try { sendInviteEmail(...) } → 成功 emailSent=true
       │    catch → console.error，emailSent 維持 false（不中斷流程）
       └─ 回傳 { inviteUrl, token, emailSent }
```

寄信失敗「不會」讓整個邀請流程崩潰，邀請本身仍會建立成功。

### 前端提示與 QRCode 備用化動線（`src/app/settings/page.tsx`）

**Email 為主、QR Code 退為備用**。共同飼主邀請以「輸入對方 Email 寄出邀請信」為主要動線，QR Code 功能保留但不再是預設動線：

依回傳的 `emailSent` 旗標給出不同提示：

| emailSent | 提示文字（中性語氣） |
|---|---|
| `true` | 「邀請信已寄出」（**不自動彈出 QR Code**） |
| `false` | 「邀請已建立，但信件寄送失敗，可改用下方 QR Code 當備用」（**寄信失敗才自動彈出 QR Code 當備援**） |

QR Code 的觸發時機分三種：

| 情境 | QR Code 行為 |
|------|-------------|
| 寄信成功 | 不自動彈出（避免干擾主動線） |
| 寄信失敗 | 自動彈出當備援 |
| 想當面分享 | 手動點「待接受邀請」列旁既有的 QR 小按鈕開啟，讓對方當面掃描加入 |

QR Modal 文案也改為備用語氣：標題「或讓對方當面掃描」、副標「邀請信已寄出；若對方就在身邊，也可直接掃描下方 QR Code 加入」。邀請輸入框下方新增動線說明文案（主：輸入 email 會寄出邀請信；次：想當面分享可點 QR 圖示）。QR Code 產生與顯示功能（`QRCode.toDataURL`、`handleShowQr`、Modal）全部保留，未刪除。

## Demo seed 機制（`prisma/seed.ts`）

seed 腳本只對「本機開發資料庫」灌入示範資料，便於本機開箱即有完整 demo 情境，不影響生產資料：

- 寫入目標由 `DATABASE_URL` 決定，預設指向本機 `dev.db`（`file:` 相對路徑會被轉成絕對路徑）。
- 所有資料以 upsert 方式建立，重複執行不會產生重複資料。
- 涵蓋的示範資料：本月多天 `DailyHealthLog`、`HealthMetric`、`MeasurementRecord`、`MedicationRecord`、`GroomingRecord`、`Product` / `PetProduct`，以及本批新增的 8 個 model——`SymptomEntry`、`ProductReaction`、`ChatMessage`、`InstantAnalysis`、`NutritionAnalysis`、`AIInsight`、`WeeklyTask`、`NewsArticle`。
- demo 產品補上 `ingredientJson`（含 `nutritional_facts` 結構），對齊 `/api/extract` 輸出與 `/api/analysis` 的期望格式，讓成分分析功能在 demo 資料上也能正常運作。

### 每日健康日誌「6 種樣態輪替」

`makeLog(offset)` 過去最近 6 天幾乎都對應「正常」樣態，看起來每天都一樣、缺乏變化。現改為**準備 6 種彼此不同的每日樣態（T0~T5）依日期輪替**（`templates[Math.abs(offset) % 6]`），讓連續幾天的日誌不會長一樣，月曆總覽的分佈也更有層次：

| 樣態 | 大致內容 |
|------|---------|
| T0 良好 | 精神飽滿、食慾正常、正常成形 |
| T1 活力充沛 | 活動意願高、胃口極佳 |
| T2 輕微軟便 | 便便偏軟 |
| T3 疲倦 | 異常疲倦、猶豫慢食、喝得少、頻尿蹲 |
| T4 腸胃+情緒 | 挑食偏食、便便偏軟帶黏液、焦躁不安 |
| T5 喝水偏多 | 異常狂喝 |

同時修正了與 UI 選項對不上的不合法值：`軟便` → `便便偏軟`、`帶黏液` 從 `stoolType` 改歸到 `stoolDetails`（多選），確保 seed 資料的單選值都採 schema 註解的合法選項，總覽才顯示得出來。

### seed 防呆（避免誤寫正式庫）

`seed.ts` 開頭檢查 `DATABASE_URL`：若有設定且**不是** `file:` 開頭（例如指向 Turso 的 `libsql://...`），就 `console.error` 提示並 `process.exit(1)` 中止，不執行任何寫入。這道防呆確保示範假資料只會灌進本機 SQLite（`dev.db`），不會因為跑 seed 時環境變數指到正式資料庫而把假資料寫進去。正確用法：`DATABASE_URL="file:./dev.db" npx prisma db seed`。

### demo / Google / 正式環境的資料策略

> 完整定案見本檔「測試 / 正式環境資料策略（frank 對齊定案）」。重點：測試環境（`dev.db`）與正式環境（Turso）為**兩個實體 DB 完全切開**；正式站不設 `DEMO_ENABLED` / `NEXT_PUBLIC_DEMO_ENABLED`，demo 完全不碰正式 Turso。

| 情境 | 資料來源 |
|------|---------|
| demo 帳號（僅測試環境啟用） | 一般資料吃 seed 灌入的示範資料；AI / 外部 / 推播一律 mock、**不落地 DB**，用於展示完整情境 |
| 其他測試帳號 / 一般 Google 登入 | 乾淨自建：自己建立毛孩與紀錄、走真實 AI，不混入 demo 假資料 |
| 正式環境 | 僅開放 Google 登入、連 Turso；**不開 demo 登入口** |

因此 seed 只服務測試環境 / demo 展示，正式使用者的資料與 mock 資料彼此隔離（且分屬不同實體 DB）。

## AI 營養師 messages 陣列設計（`/nutritionist`）

AI 營養師頁面採用完整訊息陣列傳遞設計，確保 AI 保有對話上下文：

send(userInput)
  └─ nextMessages = [...messages, { role: 'user', content: userInput }]

## 紀錄參數設定連動機制（`useRecordParams` hook）

`src/hooks/useRecordParams.ts` 定義了紀錄參數設定的核心邏輯，供設定頁寫入、日誌頁讀取，實現「設定頁 toggle → 日誌頁即時連動」。

### 資料結構

```typescript
interface RecordParam {
  id: string           // 字串 id（如 'medication'、'grooming'）
  label: string        // 繁中顯示名稱
  enabled: boolean     // 是否啟用
  group: 'shortcuts' | 'daily' | 'symptoms'  // 所屬分組
}
```

10 個參數項目，分三組：

| 分組 | id | 顯示名稱 | 影響元件 |
|------|----|--------|---------|
| 快捷紀錄（shortcuts） | `medication` | 用藥看診 | `DiaryTopBar` 按鈕 |
| 快捷紀錄 | `grooming` | 洗澡美容 | `DiaryTopBar` 按鈕 |
| 快捷紀錄 | `measurement` | 量測紀錄 | `DiaryTopBar` 按鈕 |
| 每日健康填寫（daily） | `dailyChecklist` | 每日例行清單 | `HealthLogSection` |
| 每日健康填寫 | `dietStatus` | 今日飲食狀態 | `HealthLogSection` |
| 每日健康填寫 | `appetite` | 食慾咀嚼 | `HealthLogSection` |
| 每日健康填寫 | `water` | 飲水量 | `HealthLogSection` |
| 每日健康填寫 | `stool` | 排便狀況 | `HealthLogSection` |
| 每日健康填寫 | `urine` | 泌尿狀況 | `HealthLogSection` |
| 症狀觀察（symptoms） | `healthSymptoms` | 症狀觀察 | `HealthLogSection`（allHealthy toggle + 9 張卡片） |

### 讀寫流程

```
設定頁 toggle 切換
  └─ 寫入 localStorage['purepaw_record_params']（JSON，立即寫入，不需儲存按鈕）

日誌頁 /diary 掛載
  └─ useRecordParams() hook
       └─ useEffect 呼叫 loadParams()
            ├─ localStorage 無資料 → 使用 DEFAULT_RECORD_PARAMS
            ├─ 新格式（字串 id）→ 以儲存的 enabled 覆蓋 DEFAULT
            └─ 舊格式（純數字 id）→ 自動遷移後寫回，再使用遷移結果
       └─ 傳入 { params, isEnabled }
            ├─ DiaryTopBar：props showMedication/showGrooming/showMeasurement 控制按鈕顯示；全部隱藏時整列不渲染
            └─ HealthLogSection：props params 傳入，內部 show(id) 函式控制各卡片條件渲染
```

### 舊格式遷移

早期版本的 `purepaw_record_params` 使用數字 id（如 `'2'`、`'3'`）。`loadParams()` 偵測到 id 為純數字時，透過 `LEGACY_ID_MAP` 對照表將舊 enabled 值套用至新格式，並立即覆蓋寫回 localStorage，完成一次性遷移。

### localStorage 格式

| localStorage key | 值 |
|---|---|
| `purepaw_record_params` | JSON 字串（`RecordParam[]`） |

## 健康指標記錄機制（v1.4.0 新增）

**資料模型**：`HealthMetric`（`@@unique([petId, date])`）

每日記錄三項指標：
- `bodyScore`：BCS 1–9 整數（1=極度消瘦 / 5=理想 / 9=嚴重肥胖）
- `vitality`：`"low" | "medium" | "high"`（低落/正常/活躍）
- `waterIntake`：`"low" | "medium" | "high"`（偏少/正常/偏多）

**寫入路徑**：
1. 日誌頁 `HealthMetricInput` 元件 → POST `/api/health-metrics`（upsert，同日覆蓋）
2. AI 隨記解析 → PUT `/api/diary-parse`（批次儲存，upsert 同日記錄）

**讀取路徑**：
- 首頁 `HealthMetric` 元件：GET `/api/health-metrics?petId=&date=today` → 顯示當日值
- 日曆點選 DayDetail：GET `/api/diary-records?petId=&date=YYYY-MM-DD` → 包含 healthMetric 欄位

## AI 隨記解析機制（v1.4.0 新增）

**流程**：使用者輸入自由文字 → POST `/api/diary-parse` → Claude 解析 → 返回結構化記錄列表 → 使用者確認 → PUT `/api/diary-parse` → 批次儲存

**解析類型**：
- `symptom`：症狀（皮膚/淚腺/腸胃/口腔/耳朵/關節/其他）→ `SymptomEntry`
- `medication`：用藥（疫苗/驅蟲/處方/看診）→ `SymptomEntry(symptomType='medication')`
- `grooming`：美容（居家/基礎/大美容）→ `SymptomEntry(symptomType='grooming')`
- `health_metric`：健康指標 → `HealthMetric`（upsert）
- `food_note`：飲食備注 → `SymptomEntry(symptomType='other')`

## 日常飲食搜尋機制（v1.4.0 新增 AI 搜尋）

**雙軌搜尋**：
1. **本地 DB**（300ms debounce）：搜尋 `Product` 資料表，立即顯示
2. **AI Google 搜尋**（800ms debounce）：POST `/api/products/web-search` → Claude + `web_search_20250305` 工具搜尋網路 → 返回產品資訊 + 成分分析

**AI 搜尋返回資料**：product name/brand/type/description/ingredients + 成分風險計數（toxic/warning/caution/safe）

**加入記錄流程**：點擊 AI 搜尋結果的 `+` → POST `/api/products`（建立產品） → 加入 ProductUsage

## 日曆點選紀錄機制（v1.4.0 新增）

日曆（月曆/週曆）日期有藍點 = 該日有 `SymptomEntry` 或 `ProductUsage`。

點擊日期 → `DayDetail` 面板 → GET `/api/diary-records?petId=&date=YYYY-MM-DD` → 顯示：
- 健康指標（bodyScore/vitality/waterIntake）
- 飲食紀錄（ProductUsage + 品名）
- 其他紀錄（SymptomEntry，依 symptomType 顯示中文標籤）
